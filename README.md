# Cross-repository change bench

Public benchmarks of AI code review score a pull request against **one** repository. They cannot
see the commonest way a change breaks a multi-repository system: a library drops or renames a
function, and the programs in *other* repositories that call it stop building. Nobody reviewing the
library's pull request sees those programs.

This bench measures that. It replays real changes from the history of
[NASA's core Flight System (cFS)](https://github.com/nasa/cFS), 21 repositories written in C that
are built together, and asks each tool: **which other repositories does this change break?** The
answer is checked against what actually happened: the commits in which those repositories had to be
fixed.

Every number below is regenerated by `make score` from the files in `results/`. Every file in
`results/` is regenerated by the `make` target of its tool (see [Reproducing](#reproducing)).

## Results

Three tracks. Tracks 1 and 2 have their own ground truth; track 3 reuses both. Model for every model-based row: Qwen3-Coder 30B-A3B Instruct (open
weights, Apache 2.0) through an OpenAI-compatible endpoint, temperature 0 where the tool allows it.
Grace's change impact uses no model.

### Track 1: public names removed, renamed or deprecated (10 changes, 45 broken users)

| Tool | Broken users named (of 45) | Recall | Source files of the fixes named (of 138) | Repositories named | Confirmed by a fix | Precision (lower bound) | Changes with a warning (of 10) |
|---|---|---|---|---|---|---|---|
| Grace `system impact` | 45 | 100 % | 131 | 46 | 45 | 98 % | 10 |
| Grace, "breaks" only | 35 | 78 % | 96 | 36 | 35 | 97 % | 7 |
| The model alone, diff + list of the repositories | 30 | 67 % | 0 | 142 | 30 | 21 % | 10 |
| The model alone, diff | 0 | 0 % | 0 | 1 | 0 | 0 % | 10 |
| PR-Agent 0.50.0 `review` | 0 | 0 % | 0 | 0 | 0 | n/a | 5 |

Grace sorts what it names into "breaks" (a removed name used in code) and "to check" (a deprecated
name or a changed signature): the "breaks" row counts only the first. The ten users it lists only as
"to check" are those of the two deprecations, which keep compiling until the old name goes.

### Track 2: a struct member removed while the type stays (4 changes, 10 broken users)

`OS_time_t.microsecs`, `CFE_SB_TlmHdr_t.BaseMsg`, `CFE_MSG_Message_t.Byte`, `SpacePacket`: no public
name disappears, so a reading by names cannot see them. This track was built after the first one,
to measure what Grace missed; Grace was then taught to read struct members, and both versions are
scored.

| Tool | Broken users named (of 10) | Recall | Repositories named | Confirmed by a fix | Precision (lower bound) | Changes with a warning (of 4) |
|---|---|---|---|---|---|---|
| Grace, with struct members | 10 | 100 % | 22 | 10 | 45 % | 4 |
| Grace, with struct members, "breaks" only | 9 | 90 % | 11 | 9 | 82 % | 3 |
| Grace before (names only) | 5 | 50 % | 17 | 5 | 29 % | 2 |
| Grace before, "breaks" only | 1 | 10 % | 3 | 1 | 33 % | 1 |
| The model alone, diff + list of the repositories | 6 | 60 % | 47 | 6 | 13 % | 4 |
| The model alone, diff | 0 | 0 % | 1 | 0 | 0 % | 4 |
| PR-Agent 0.50.0 `review` | 0 | 0 % | 0 | 0 | n/a | 1 |

A removed member counts as used only through `.member` or `->member`, and only where one of its
types is named: in the file ("breaks"), elsewhere in the repository ("to check"), or nowhere (another
member with the same name, not counted). Grace's "to check" on track 2 are mostly applications that
call functions the same change deprecated: true, but not a breakage, so not in the truth.

The same tracks with a smaller model, Qwen2.5-Coder 7B on a laptop (`results/qwen2.5-coder-7b/`,
track 1), give the same picture.

"Changes with a warning" counts a review that says code outside the repository may break, even
without naming it; it is decided by hand, and every decision is in `adjudication.json` next to the
scores. Every repository named but not confirmed is listed per change in `SCORES.md`.

**Read this before the numbers.** Both truths were found by mining the history for something a
program can look for (a name, a member), then read by hand. Breakages that leave no such trace are
in neither: messages on the software bus, a change of behaviour behind an unchanged signature, a
build file. Searching the history for them found nothing that could be tied to a fix; on those,
Grace is not measured. What the bench does show is the gap between a tool that reads only the
changed repository and one that reads the whole system.

### Track 3: did the debt show before it broke? (14 changes)

Tracks 1 and 2 ask what a change breaks once it is written. This track asks the earlier question:
on the system **as it was just before** each of the 14 changes, did Grace's scan point at the
interface that was about to break? Two parts of Grace are scored. Its deterministic detectors
(coupling, hubs, unstable interfaces, deprecated code, ...) use no model. Its *interface debt* step
gives the headers that the most other repositories use to a model, which reads each one as a contract
and reports what works today but will make its users break when the header changes. Every finding
quotes a line of the header, and a quote not found in the file is discarded.

Model: Qwen3.8 27B (open weights) through the same endpoint, temperature 0. Grace at commit
`9051f98d`.

| Did Grace point at it beforehand? | Changes (of 14) |
|---|---|
| a deterministic detector names a broken name or its type | 0 |
| the model reports interface debt on the header that broke | 5 |
| the model names the very symbol or member that broke | 2 |

The two named: before `CFE_SB_TlmHdr_t.BaseMsg` broke four applications (F02), the model reported
that the union exposed `Cmd` and `BaseMsg` and that "users that read or cast Cmd/BaseMsg must
change". Before `SpacePacket` and the CCSDS packet types went (F04), it reported the byte array
`Byte[sizeof(CCSDS_PriHdr_t)]` and the deprecated alias `CCSDS_CmdPkt_t` kept alive. Every finding,
with its quote and its reason, is in `results/debt/raw/<id>.json`, and the per-change detail in
`results/debt/SCORES.md`.

**Read this before the numbers.**
- The model read 15 headers per snapshot, chosen by how many other repositories use them, and all
  15 were cFE's every time. The 7 changes in osal, PSP and EdsLib had no chance: the score is 5 of
  the 7 cFE changes at the header level, 0 of the 7 others. Grace now takes the shared headers
  in turn by repository (8 cFE, 7 osal on these snapshots); that version was not run here.
- It is noisy: about 75 interface debts per snapshot, so the hits stand among many warnings that
  have not broken anything (yet). Precision is not measured: a debt that has not broken yet is not
  wrong.
- "Names the symbol" also counts the type a broken member belongs to (`CFE_SB_TlmHdr_t` for
  `BaseMsg`).
- The deterministic detectors find the shape of the system (who depends on whom), not the content of
  an interface: none of them pointed at a symbol that later broke.

## The ground truth

`truth.json` holds **10 changes** to a shared repository (cFE, OSAL, PSP, EdsLib) and **45 cases**:
a repository that used what the change removed, renamed or deprecated, and the commit in which that
repository had to be fixed. It is generated from `cases.txt` by `tools/build_truth.py`, which only
resolves commit ids and lists the source files each fix changed.

How the cases were found, then checked by hand:

1. Every commit of the shared repositories that removes a public name from a header (a function, a
   macro, a type) whose name no longer exists in that repository afterwards.
2. For each, the commits of the *other* repositories, from two weeks before to six months after,
   that edit a line using that name.
3. Each pair was read, both diffs. A pair is kept when the user's fix is about that change (its
   message or its timing ties it to the change), not a coincidental edit. Changes in which only a
   copy of a definition moved were dropped.
4. For the 10 changes kept, every other repository was searched for the first commit, within three
   years, that removes a line of code using one of the change's names. Those are the `later` cases:
   the repository was broken by the change and fixed later, often in a release.

| Evidence | Cases | Meaning |
|---|---|---|
| `direct` | 21 | the user's own fix, tied to the change by its message or timing |
| `release` | 6 | a release of the user that swaps the old names for the new ones |
| `later` | 18 | the first later commit of the user that removes a use of the names |

Each case carries the URL of both commits. The kinds of change: names removed (5 changes), renamed
(3), deprecated with the old name kept for a while (2).

`truth-fields.json` (track 2) is built the same way from `cases-fields.txt`: every struct or union
member removed from a public header of a shared repository, then the users that edited a
`.member` or `->member` access to it. Four changes and ten users were kept after reading; candidates
where the user's field was its own (same name, its own struct) were dropped.

**The truth is incomplete by construction.** A repository that used a removed name and was never
fixed, or was fixed by deleting a whole file, is not in it. So a tool that names a repository the
truth does not list is not necessarily wrong: precision is a **lower bound**, and the per-change
detail in `results/SCORES.md` lists every unconfirmed repository so you can check it yourself.

## What each tool is given

The system as the author of the change saw it (`snapshots.json`): the changed repository at the
parent of the change, every other repository at its last commit before the change, or before its own
fix when that came first (some users adapted while the change was under review).

| Tool | Given | How its answer is read |
|---|---|---|
| Grace (`grace system impact`) | the change and the snapshot of all 21 repositories | its JSON: every repository where it found a use in code |
| PR-Agent (Qodo, open source) `review` | the change, as a pull request on a local clone of the changed repository | the repositories its review names |
| The model alone, diff | the diff, and the question "which code outside this repository could this break?" | the repositories it names |
| The model alone, diff + list | the same, plus the names of the 20 other repositories | the repositories it names |

The three model-based rows use the same open-weight model (see [Results](#results)). Grace's answer
to this question uses no model at all: it reads the headers and searches the other repositories, so
it gives the same answer on every machine.

A repository name in a review counts when it appears as a word. Names of three letters or fewer
(`CF`, `DS`, `HK`…) must match their case exactly, since lower-case `ds` or `md` are ordinary words.
A file counts when the answer gives its path or, for a free-text review, its file name.

## Reproducing

```bash
make setup          # clone the 21 repositories into work/repos (read-only, from GitHub)
make score          # recompute every number from results/ (three tracks, and the 7B run)
make grace          # needs Grace's engine: GRACE="uv run --project <grace>/engine grace"
make pr-agent       # needs pip install pr-agent==0.50.0 and PR_AGENT_PYTHON
make model          # needs an OpenAI-compatible endpoint: API_BASE, MODEL, API_KEY
make debt           # track 3: needs Grace's engine (GRACE_ENGINE=<grace>/engine) and an endpoint
make truth snapshot # rebuild the truths and snapshots from cases.txt and cases-fields.txt
```

`TRACK=fields make grace` (or `pr-agent`, `model`) runs a tool on track 2. `bench.py` uses only the
Python standard library.

Grace is a commercial product of Beyond The Brackets, and `make grace` needs its engine. You do not
need it to check Grace's numbers: its raw answers are in `results/raw/grace/` and
`results/fields/raw/grace*/`, one JSON per change,
with every file and line it names, and `make score` reads them like any other tool's.

## Limits

- One system, one language (C), and changes to *declared* interfaces only. Breakages through data
  (messages on the software bus, shared tables), behaviour, or build files are not in the truth.
- 10 and 4 changes is small. They were chosen because their consequences are documented, not at
  random.
- The commercial review tools were not run on the cross-repository changes: they work through pull
  requests on a hosted forge, and this bench opens none on anyone else's project.
- The authors of this bench make Grace. The truth, the snapshots, every tool's raw output and the
  scoring code are here so that anyone can check the numbers without trusting us.

## A public pull-request review bench, for scale

The card behind this bench also asked for a score on a public review bench, to place Grace on the
question every other tool answers: a pull request in one repository. `pr-bench/` runs Grace's
review on 5 pull requests of [Martian's code review bench](https://github.com/withmartian/code-review-benchmark)
(the first of each of its five projects) and scores it with the bench's own pipeline (extract,
deduplicate, judge). The judge is Qwen3-Coder 30B-A3B, not the frontier models of the published
leaderboard, so the six best-known tools were re-judged by the same model on the same pull requests,
from the reviews the benchmark publishes. Every tool was judged three times: on five pull requests,
one judgement of the same reviews moved by 12 points of F1. The figure is the mean, with the range.

| Tool | Its model | Precision | Recall | F1, Qwen3-Coder judge (3 runs) | F1, published judge (GPT-5.2), same PRs |
|---|---|---|---|---|---|
| Qodo | hosted | 52 % | 57 % | 54 % (50 to 61) | 30 % |
| **Grace** | **Qwen3.8-27B (open weights)** | **41 %** | **59 %** | **48 % (48 to 49)** | not published |
| Claude Code | hosted | 48 % | 45 % | 46 % (42 to 48) | 40 % |
| Cursor Bugbot | hosted | 58 % | 37 % | 45 % (43 to 50) | 36 % |
| CodeRabbit | hosted | 39 % | 51 % | 44 % (42 to 46) | 41 % |
| GitHub Copilot | hosted | 35 % | 55 % | 43 % (41 to 45) | 26 % |
| Grace | Qwen3-Coder-Next (open weights) | 34 % | 57 % | 43 % (39 to 44) | not published |
| Greptile | hosted | 41 % | 37 % | 39 % (38 to 42) | 21 % |
| Grace | Qwen3-Coder 30B-A3B (open weights) | 24 % | 39 % | 29 % (26 to 31) | not published |

With a 27-billion-parameter open-weight model, which a customer can host, Grace's review comes
second on these five pull requests, behind Qodo. The local judge is more lenient than the published
one (by 6 to 21 points of F1), so only the Qwen-judge column compares tools. Five pull requests is a
small sample: read the order, not the decimals. The next step is the full 50 pull requests with the
published judge, which would put Grace directly on Martian's leaderboard.

How it got there, measured on the same five pull requests:

| Grace's review | Comments (Qwen3-Coder 30B) | F1 |
|---|---|---|
| As it was: an audit of the changed files and their neighbours, keeping findings on changed files | 66 | 12 % (one judgement) |
| The model is shown the diff and asked for the defects the change introduces, at most 8, duplicates removed, serious findings never dropped, decorated locations read | 29 | 29 % with Qwen3-Coder 30B, 48 % with Qwen3.8-27B (three judgements) |

Running this also found two defects in Grace, fixed before any score: a server that accepts
`json_schema` without enforcing it (LM Studio with an MLX model) made every review answer read as
"nothing to report"; and the review never told the model which files the pull request changed.

```bash
pr-bench/fetch.sh     # the 5 diffs and pull-request heads, read-only, from GitHub
TOOL=grace-<model> INTERNAL_BASE_URL=... INTERNAL_CHAT_MODEL=... uv run --project <grace>/engine python pr-bench/run_grace.py
RUNS=3 pr-bench/judge.sh   # the benchmark checked out in work/pr-bench/martian; API_BASE, MODEL, API_KEY
```
